> 版本：v1.1（评审稿） · 日期：2026-10-07

>

> ① 每页面可单独设置刷新率，支持小数（最低 0.2s，服务动画型页面）；② 每页面可单独调 JPEG 质量；③ 设置项统一收口到管理后台 `/setting`；④ 电脑浏览器客户端同步支持极速模式；⑤ 不再为省服务器资源做过度设计（可扩容）。

## 1. 背景与目标

机房动环监控、虚拟化集群资源监控、大模型服务状态监控三个页面都是重型监控大盘：电视端要用 Chrome 66 老内核跑 2MB 级 bundle、维持 WebSocket/轮询并实时重绘，受限于电视性能，加载慢、操作卡。

**极速模式**把"渲染"从电视搬到服务器：服务器用无头浏览器打开真实页面并周期性截图，电视/电脑端只显示一张不断刷新的 JPEG。预期收益：

| 指标 | 现状（真实页面） | 极速模式 |
|---|---|---|
| 电视端 CPU | 跑完整 JS + DOM 重绘 + WebSocket | 每周期解码 1 张 1080p JPEG（约 30~80ms） |
| 首屏时间 | 白屏等 bundle + 登录 + 首批数据，数秒~十几秒 | 热启动 ≤3s；冷启动 ≈5~10s（之后恒定） |
| 兼容性 | 依赖转译/垫片/视口修补 | 纯图片页，Chrome 66 兼容问题全部失效化 |
| 交互 | 完整 | 只读（缩放仍可用；保留切回真实页面的逃生通道） |

与现有机制**并存**：极速模式是本机开关（默认关），关掉后一切照旧。

## 3. 总体架构

```
服务器（10.8.11.4:18000）                                电视端（WebView）/ 电脑浏览器
┌───────────────────────────────────────────┐
│ shot.js（新增采集模块）                     │
│  ┌─────────────────────────────────┐      │   GET /shot/<id>/view  → 包装页(HTML)
│  │ Headless Chromium（单实例多标签） │      │  ┌──────────────────────┐
│  │  标签=入口：动环 / 虚拟化 / AI …  │      │  │ <img>×2 双缓冲淡入    │
│  │  每入口一个采集循环               │ ────→ │  │ setInterval 换帧      │
│  │  周期/质量 = 该入口后台配置       │      │  │ sendBeacon 心跳/5s    │
│  │  登录会话保活（复用 autoLogin）    │      │  │ 离线/定格提示浮层      │
│  └─────────────────────────────────┘      │  └──────────────────────┘
│  最新帧驻留内存；多端共享同一帧              │   播放端零 JS 执行、零 WebSocket
└───────────────────────────────────────────┘
```

核心原则：**一次采集、多方观看**。不管几台设备看同一入口，服务器只有一个采集循环，周期与质量完全由该入口的后台配置决定（不再按观看者协商，v1.1 简化）。

## 4. 服务端设计

### 4.1 配置模型（config.json 新增字段，随 version 下发）

每个入口（`type=url`）新增 3 个字段，与 `compatTranspile` 同风格平铺：

| 字段 | 类型/默认 | 说明 |
|---|---|---|
| `turboEnabled` | bool，默认 `true` | 该页面是否参与极速模式。所有现有/新增页面默认参与；个别不需要的页面可在后台单独关掉 |
| `turboIntervalSec` | number，默认 `2` | 该页面刷新率（秒）。**支持一位小数**，范围 `0.2 ~ 60`；如动画型页面可设 `0.5`、`0.2` |
| `turboQuality` | int，默认 `75` | 该页面 JPEG 质量，范围 `50 ~ 95`；动画多/文字小的页面可调 85~95 换清晰度（体积随之增大） |

- 管理后台校验扩展（并入现有 8 类参数校验体系，非法返回 400 并提示具体原因）：
  - `turboIntervalSec`：必须是 0.2~60 之间的数，最多一位小数；
  - `turboQuality`：50~95 的整数；
  - `turboEnabled`：布尔。
- 旧客户端（v1.6 及更早）读到这 3 个字段会忽略，不受影响；无需动 epoch（字段是新增，不影响 304 合并，但**建议发布时 bump 一次 epoch** 保证全量下发）。
- 服务端 `/api/config?full=1` 与增量 delta 均携带新字段。

### 4.2 新增模块与依赖

| 项 | 说明 |
|---|---|
| 新文件 | `server/shot.js`（采集状态机 + Chromium 管理 + HTTP 路由）；包装页模板内嵌于 shot.js（与 proxy shim 同风格） |
| 依赖 | `playwright-core`（npm，仅驱动）+ Chromium 浏览器二进制（`npx playwright install chromium`，约 300~500MB 磁盘） |
| 约定 | 沿用 esbuild 先例：**可选依赖**。Chromium 不可用时 shot 路由返回降级包装页（内嵌说明 + 跳转真实页面），服务端本体照常启动，`/api/admin/health` 增 `shot: {available, reason, activeEntries}` 字段 |
| 资源 | 不做严苛限制（用户已确认可扩容）。参考值：每入口标签 100~300MB 内存；并发 10 入口 × 1s ≈ 1 核满载——按此估算扩容 |

### 4.3 采集状态机（每入口一个）

```
            有人看(心跳≤12s)                 无人看
 STOPPED ────────────────→ STARTING ──→ ACTIVE ────────→ COOLING(30s)
   ↑                        │  冷启动     │  按后台配置周期截图   │ 仍无人看
   │  冷却满30分钟            │  开页+登录  │                     ↓
   └──────────────────────── ┴←── 热启动 ←──┴←── 有人回来看 ── PAUSED
                                 （≤3s，标签与会话仍在）
```

| 状态 | 行为 |
|---|---|
| STOPPED | 不占资源。有观看者时进入 STARTING |
| STARTING | 打开标签（1920×1080、deviceScaleFactor=1、`allowInsecureSsl` 时忽略证书）→ 登录（4.4）→ 截首帧 → ACTIVE |
| ACTIVE | 按**该入口后台配置**的 `turboIntervalSec` 周期截图；周期被后台修改时下一帧立即生效（无需重启采集） |
| COOLING | 无人观看后保活 30s（防电视切页/重启抖动），再暂停进 PAUSED |
| PAUSED | 停止截图但**保留标签与会话 30 分钟**（热启动 ≤3s）；期满无人则关标签回 STOPPED |

### 4.4 截图参数与刷新率下限

| 参数 | 值 | 说明 |
|---|---|---|
| 视口 | 1920×1080，deviceScaleFactor=1 | 与大屏设计分辨率一致 |
| 格式 | JPEG，质量=该入口 `turboQuality` | 单帧约 150~300KB（q75）；q90 约 300~500KB |
| 截图方式 | `page.screenshot({type:'jpeg'})`，非 fullPage，`animations:'disabled'` | 减少半帧撕裂 |
| 单帧超时 | 5s | 超时跳帧、保留旧帧，不阻塞循环 |

**刷新率下限说明（重要）**：一次截图（viewpoint 提交 + 编码）在服务器上约 100~250ms，因此：

- `0.2s`（5fps）是**理论档位**，仅适合轻量页面；
- `0.2 ~ 0.5s` 档位验收时按页面实测：若截图耗时 ≥ 间隔，采集循环自动跳帧（按"上一帧完成时刻 + 间隔"调度），**不会积压**；
- 动画型页面的推荐值：`0.5s`（流畅且稳定）；确实需要更快的页面，实测后再下调。

### 4.5 登录与会话保活

- 直接访问**上游真实地址**（`entry.url`），不走 proxy（截图不需要改写）。
- 复用现有 `entry.autoLogin` 字段（`username/password/usernameSelector/passwordSelector`，与 proxy 注入自动登录同一份配置），服务端在无头页里执行等价的"填账号→填密码→提交"流程。
- 登录成功后 storageState 落盘 `server/.cache/shot/<id>/state.json`，冷启动先恢复会话，多数情况跳过登录。
- 每帧截图前轻量检测登录态（URL 含 login / 出现密码框即掉线），掉线自动重登；**连续 3 次失败**停手，帧定格最后成功画面并置 `meta.status="login_failed"`，之后每 5 分钟重试一次。
- 账号密码等敏感字段**不出现在任何 /shot 响应**中，只在服务端内存使用。

### 4.6 HTTP API

| 路由 | 方法 | 说明 |
|---|---|---|
| `/shot/<id>/view` | GET | 包装页 HTML。刷新率/质量由服务端按该入口配置**内联注入**包装页（不经 URL 参数）；未知入口 404；camera 入口 404 |
| `/shot/<id>/frame.jpg?t=<nonce>` | GET | 最新帧 JPEG。`t` 仅击穿缓存；`Cache-Control: no-store`；尚无帧返回 503（包装页显示"准备中"） |
| `/shot/<id>/meta.json` | GET | `{status:"active|starting|paused|login_failed|error", ts:<帧时间戳>, interval:<当前周期s>, quality, title}` |
| `/shot/<id>/beat` | POST | 心跳，204 无响应体。body 仅含观看者会话 id |

安全：与 `/api/config` 同级（内网开放）；条目 id 校验防穿越；心跳只更新内存 Map，不落盘。

### 4.7 包装页规格

- **ES5 编写**（目标 Chrome 66，与 compat 垫片同一底线），单文件、无外部依赖，电视端 WebView 与电脑浏览器通用。
- 双缓冲：两张叠放 `<img>`，新帧 decode 完成后再切换 `opacity`（150ms 淡入），**避免白闪**。
- 循环：`setInterval`（周期=内联注入的该入口配置）拉取 `frame.jpg?t=Date.now()`；连续 3 次失败降频 3 倍并显示"画面同步中…"，恢复后自动回正常频率。
- 心跳：`navigator.sendBeacon('/shot/<id>/beat', …)` 每 5s；`pagehide`/`beforeunload` 补发一次（让服务端尽快进入 COOLING）。
- 浮层（左下角，白字半透明底，与现有信息浮层同风格）：
  - 时间戳 `HH:mm:ss`（取 meta.ts）；
  - 状态水印：`极速模式 · 2s`（间隔来自 meta，便于现场核对后台配置是否生效）；
  - 异常水印：`准备中 / 采集异常 / 登录失效`；出错时附 `菜单 返回真实页面` 提示。
- 不拦截遥控器/键盘按键；菜单弹窗由客户端原生层负责。

### 4.9 机房监控（type=camera）的处理

机房监控画面墙是**原生 MJPEG**（服务端 ffmpeg 按行合成 + 客户端直连视频流），本身已是"服务端出图、播放端只解码"的最轻路径，且是活动视频而非网页。结论：

- **不纳入极速模式**，开启极速模式后机房监控行为完全不变（刷新率/JPEG 质量设置对 camera 入口不显示）；
- 客户端/Web 端在极速模式下对 `isCamera` 直接走原逻辑；
- 包装页对 camera 入口返回 404，作为服务端兜底。

## 5. 电视端客户端设计（v1.7，versionCode 16）

### 5.1 参数来源：全部来自服务端配置

v1.1 修订：刷新率、质量、页面参与开关**不再存本机**，统一随 config.json 同步下发（要点 8）。本机只保留一个**总开关**（要点 1）。

```kotlin
// LocalSettings.kt 仅新增：
data class TurboSetting(val enabled: Boolean = false)   // 本机总开关，默认关
```

### 5.2 客户端模型与缓存

- `AppConfig.DisplayEntry` 新增 `turboEnabled: Boolean`、`turboIntervalSec: Double`、`turboQuality: Int`；`ConfigJson.parseEntry` 解析、`ConfigStore.toJson` **逐字段写全**（踩坑教训：漏写即 304 后永远补不回）。
- `CACHE_SCHEMA` 2 → **3**：升级时作废旧缓存全量重拉，确保老电视升级 APK 后立即拿到新字段。
- 旧字段缺失时的默认值与服务器一致（true / 2 / 75），包内兜底 `assets/config.json` 同步补齐 3 字段。

### 5.3 地址切换

```kotlin
// AppConfig.kt 新增：
fun turboUrlOf(entry, serverBaseUrl) = "$serverBaseUrl/shot/${entry.id}/view"

fun effectiveUrlOf(entry, serverBaseUrl): String =
    when {
        entry.isCamera                             -> 原 camera 逻辑（不变）
        LocalSettings.turboEnabled &&
            entry.turboEnabled                     -> turboUrlOf(entry, …)
        else                                       -> displayUrlOf(entry, …)  // 原逻辑含转译代理
    }
```

调用点：`WebDisplayActivity`（单页 + 轮询模式）、`ZoneDisplayActivity`（4 格 iframe 各自应用）、`MainActivity`（打开单页的 intent）。

### 5.4 菜单入口（本机总开关）

| 位置 | 新增项 | 行为 |
|---|---|---|
| 首页「更多 ▾」菜单（低频组） | `极速模式：关 / 开` | 翻转本机开关；开启时提示"已开启极速模式（各页面刷新率见后台设置）" |
| 展示页/轮询页【菜单】弹窗 | 同上 | 翻转后**立即用新地址重载当前页** |
| 分区页【菜单】弹窗 | 同上 | 翻转后 4 格全部重载 |

信息浮层新增一行：`极速模式 · 帧 Ns 前`（取 meta.ts，现场判断采集是否存活）。

### 5.5 展示页行为

- 极速地址页同样受视口控制（1920×1080 铺满）与 100vh 修补；白屏探测保留但仅兜底（图片页不会触发语法类白屏）。
- 缩放（−/＋/重置）作用于 WebView 整体，对图片页照常可用。
- 【菜单】→「刷新页面」= 重新拉一次 `frame.jpg`；「返回首页」照旧；「菜单 → 打开真实页面」为逃生通道（临时切回原地址，仅本次生效）。

### 5.6 轮询展示

- 轮询按 `intervalSec` 顺序加载各入口：极速模式下每个入口加载 `turboUrlOf`，切页即换 URL。
- 首帧体验：切页黑屏约 1~2s（首帧解码前）。可选优化"切页前 1~2s 后台预加载下一入口"，列为二期（决策点见 11.3）。

### 5.7 分区展示

- 4 格 iframe 各加载对应入口 `/view`，独立心跳与刷帧；并发 4 路采集不做限制（用户已确认可扩容）。

### 5.8 版本与发布

- `versionName="1.7"`、`versionCode=16`（严格递增），签名 v1+v2+v3 不变；
- **升级顺序：先部署服务端（含后台配置），再装 v1.7**；旧 APK + 新服务端无影响（不会访问 /shot）；
- 发布时 `POST /api/admin/epoch/bump` 一次，保证全量下发新字段。

## 7. 关键机制细节

### 7.1 带宽与性能预算（q75 估算，供扩容参考）

| 场景 | 采集负载（服务器） | 带宽（每台设备） |
|---|---|---|
| 单入口 2s | ≈10% 单核 | ≈ 0.6~1.2 Mbps |
| 单入口 0.5s（动画页） | ≈40% 单核 | ≈ 2.4~4.8 Mbps |
| 分区 4 格 2s | ≈40% 单核 | ≈ 2.4~4.8 Mbps |

### 7.2 无人观看判定

- 观看者 = 近 12s 内有心跳的会话（包装页生成随机会话 id 存 sessionStorage）；
- 心跳 3 次丢失即离开；`pagehide` 补发让单页退出在 5s 内被感知；
- 30s COOLING 防抖 + 30min PAUSED 热保活。

### 7.3 失败与降级矩阵

| 故障 | 表现 | 恢复 |
|---|---|---|
| 上游站点打不开 | meta.status=error，帧定格最后成功画面 + "采集异常"水印 | 循环每 15s 重试 |
| 登录失效且重登 3 次失败 | meta.status=login_failed，水印"登录失效" | 每 5 分钟自动重试；人工核对后台账号 |
| Chromium 崩溃 | 守卫重建 browser，包装页显示"准备中" | 自动 |
| 服务器未装 Chromium | `/shot/*` 返回降级包装页（含真实页面跳转），等同没开极速 | 安装后无需动客户端 |
| 播放端网络抖动 | 包装页降频拉帧 + "画面同步中" | 自动 |
| 后台改了刷新率/质量 | 下一帧立即生效（ACTIVE 中热更新），包装页水印同步变化 | — |

## 9. 测试与验收

### 9.1 服务端自动化（test-run.mjs 新增，无 Chromium 时标注 SKIP）

- `/shot/未知id/*` 全部 404；camera 入口 404；
- 后台校验：`turboIntervalSec=0` / `61` / `1.25`（两位小数）/ `abc` → 400 并提示；`turboQuality=49/96` → 400；合法值 `0.5`/`85` → 200 且 config 中落盘；
- 无观看者不采集（health 的 shot.active=0）；心跳后 `frame.jpg` 503→200、meta.ts 前进；停心跳 30s 后 active 归零；
- 后台热更新：ACTIVE 中改 `turboIntervalSec`，meta.interval 下一帧跟随；
- 包装页断言：ES5 无 `??`/`?.`、含双缓冲与 sendBeacon、内联间隔与配置一致；
- 敏感字段不出现在任何 /shot 响应；客户端快照含 3 个新字段且不含敏感配置。

### 9.2 端到端（开发机 Playwright，模拟 Chrome 66 API 面）

- 三个真实入口：包装页打开 → 首帧 ≤10s → 连续 3 帧时间戳推进；
- 双缓冲无白闪（连续截屏比对，切换期中间亮度无深谷）；
- 登录型入口（虚拟化/AI）会话恢复：重启服务端后首帧 ≤5s；
- 0.5s 档位实测虚拟化页：帧率、CPU、跳帧情况出数据。

### 9.3 现场验收清单

1. 后台为动环页设 0.5s、AI 页设 1s，电视端确认水印显示对应间隔、动画流畅；
2. 首页「更多」开启极速模式 → 三个慢页面确认为图片页且流畅；
3. 轮询、分区在极速模式下正常；机房监控行为与之前完全一致；
4. 电脑浏览器 `/app` 开启极速模式，同一入口与电视端看到同一帧序列；
5. 后台把某页面 `turboEnabled` 关掉 → 该页面电视端自动回退真实页面（其他页面不受影响）；
6. 电视退出播放 1 分钟后服务器 shot 活跃数下降；重新进入 ≤3s 出图；
7. 对照组：关闭本机总开关后一切回到现状（转译/视口修补照旧）。

## 11. 决策记录与遗留项

| 原决策点 | v1.1 结论 |
|---|---|
| 默认刷新率 | 每页独立，默认 2s；动画页可到 0.2~0.5s（实测下限） |
