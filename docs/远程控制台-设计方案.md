# 多设备互控 · 设计方案（v6）

> **修订记录**
> v6 按用户决议修订：**受控端一律不提供「取消控制」入口**（Web 与电视皆然）——现场想摆脱受控画面就做正常退出操作（Web 端点任意东西，电视端按【返回】退出当前画面，锁定已放行【返回】键）；状态翻转（取消控制）只存在于控制台（二次确认保留）。§8 的设备端开关 / `switchTo` 意图机制从客户端移除（服务端协议字段保留兼容）。
> v5 按用户现场反馈修订（关键架构调整）：① **控制与显示分离**——控制界面独立为单文件页面 `/console`（`server/console.html`，自身不注册为受控设备，操作者永远不会被自己锁住）；显示端首页 `/` 恢复 1.7 纯净形态（无开关、无菜单项、无控制屏）。② **Web 显示端被控不锁定**：被控只是"远程换了台"，鼠标 / 键盘始终可用（v4 的 Web 锁定 + 开关导致现场页面点不动，废弃；§8 的锁定与开关仅适用于电视端）。③ 电视端（APK 1.8）保留 v4 行为：锁定遥控按键 + 【菜单】首项模式开关 + 退出二次确认。④ 场景预设、同相轮询默认关等决议不变。
> v4：模式开关（服务端权威 + 即时影子 + 心跳捎带意图）、退出二次确认、场景预设正式功能、IP 变化分析。
> v3：受控无条件、指令即强制接管；场景预设正式功能；同步轮询默认关；电脑 IP 变化影响分析。
> v2：取消控制端/被控端角色划分——设备共三类（电脑/平板/电视），电脑与平板均以浏览器访问，电视以 APK 运行；**所有 Web 客户端既可控制、也可被控**，电视只能被控。
> 本文档只做设计，不含实现。实现记录见 `docs/远程控制台-实施规划.md`。

## 一、设备与角色模型

| 设备类型 | 运行形态 | 控制别人 | 被别人控制 | 身份载体 |
| --- | --- | --- | --- | --- |
| 电脑 ×3 | 浏览器打开 `http://<服务器>:18000/`（kiosk 常开） | ✅ | ✅ | `localStorage` 中的 deviceId |
| 平板 | 同上（主要用作控制端，触摸操作） | ✅ | ✅ | `localStorage` 中的 deviceId |
| 电视 ×2 | APK 常开 | ❌ | ✅ | SharedPreferences 中的 deviceId |
| 服务端 | 中立的指令交换所 | — | — | 不感知"谁是控制者" |

由此带来的设计含义：

1. **控制能力内置于 Web 客户端本身**：客户端新增「设备控制」screen，而不是独立的特权控制台页面。任何浏览器打开系统就同时拥有"被控"与"控制"两种能力；平板只是最顺手的控制端，电脑同样能控。
2. **任何 Web 客户端都是受控设备**：打开页面即自动注册、心跳、领指令——包括平板自己（其卡片出现在设备列表里，标记"本机"）。
3. **受控体系无开关，模式有开关（v4 修订）**：不存在"不注册 / 退网"之类的选择——任何指令都**必然自动接管**，设备无法拒绝；但每台设备都有一个随时可达的**「本地控制 / 远程被控」开关**，现场人员用它交还本地，控制端再下发即再次接管（见第八节）。
4. **服务端不区分角色**：`/api/ctl/send` 不携带也不校验调用者身份，谁调用都一样——与既有管理后台"内网免鉴权"的信任模型一致（见第十三节安全）。
5. **电视 APK 只实现受控半边**：心跳 + 指令应用 + 模式开关（在【菜单】里），没有控制界面。

## 二、背景与现状约束

系统现状（与本设计相关的部分）：

| 层 | 现状 | 与互控的关系 |
| --- | --- | --- |
| 服务端 `server/server.js`（18000，零依赖） | 内容唯一数据源：页面列表、标题、摄像头配置；增量同步协议 `/api/config?since=&epoch=`；管理后台 `/setting` | **内容通道不动**。"这台设备显示什么"与全局内容是两回事 |
| 电视端 APK（4 个界面） | 首页 `MainActivity`、单页/轮询 `WebDisplayActivity`（`EXTRA_ENTRY_ID` + `EXTRA_ROTATION`）、分屏 `ZoneDisplayActivity`、画面墙 `CameraWallActivity` | 轮询/分区是**本机设置**（`LocalSettings` → SharedPreferences），服务端不存、不下发 |
| 电脑浏览器客户端 `/` | 同款功能的网页版：home / display / camera / zone 四个 screen；轮询/分区存 `localStorage['tvshow.localSettings']` | 同上，本机设置 |
| README 已知限制第 16 条 | "轮询是各台电视各自配置的……无法统一下发本机设置" | **本设计要解决的就是这一条** |

痛点：设备作为大屏常年挂墙运行，遥控器/鼠标不在手边时，无法切换任何一台设备的展示状态。

## 三、设计原则

1. **内容通道零改动**：`/api/config` 增量同步、缓存、离线兜底全部保持原样。互控走一条**新增的、独立的"设备控制通道"**，数据放在独立文件 `server/data/devices.json`，两套版本号（内容 `version` / 指令 `seq`）互不干扰。
2. **Web 客户端一体两面**：同一份客户端代码同时实现"受控"（心跳 + 指令应用 + 模式开关）与"控制"（设备控制 screen）两个能力，不按设备类型拆分代码路径；电视 APK 只裁掉控制半边。
3. **指令即接管，开关可交还，再指令再接管**：展示类指令下达，设备无条件自动切为远程被控（本地无法拒绝）；现场人员用模式开关随时交还本地；控制端再次下发，又自动切回。**"远程被控"是动态的驾驶权归属，不是门禁。**
4. **存储转发，控制端不必常开**：控制操作只负责"写入期望状态"；设备离线时指令暂存于服务端，设备下次心跳即领取。发完指令平板就可以锁屏走人。
5. **指令覆盖而非排队**：每台设备只保留**最后一条**期望状态（desired）。语义是"把这块屏调到某个状态"，不是消息队列。
6. **向后兼容**：控制通道对老客户端完全不可见。未升级的设备只是不出现在设备列表里，其余行为不变。
7. **沿用既有工程约定**：服务端零依赖（Node 内置模块）、单端口 18000、无框架单文件页面、客户端不引第三方库（Android 用 `HttpURLConnection`，浏览器用 `fetch`）。
8. **传输从简**：v1 用普通 HTTP 短轮询心跳（3 秒一拍）；长轮询/SSE 作为后续升级路径（见第七节选型对比）。

## 四、总体架构

```
任意 Web 客户端（电脑浏览器 / 平板浏览器，打开 http://<服务器>:18000/）
   │
   ├─ 被控半边：POST /api/ctl/beat（3s 一拍）— 注册/心跳/上报状态/领指令/同步模式开关意图
   │
   └─ 控制半边（客户端内置「设备控制」screen）：
        ├─ GET  /api/ctl/devices   每隔 3s 刷新设备列表与状态
        └─ POST /api/ctl/send      下发指令 / 取消控制 / 应用场景
        ▼
┌───────────────── 服务端（仍只有一个 18000 端口）─────────────────┐
│  config.json   内容数据源（现有，完全不动）                        │
│  devices.json  设备档案 + desired + managed + 场景（唯一新增存储）  │
│  /api/ctl/*    控制通道接口（新增）                                │
│  /console      设备控制 screen 的直达别名（客户端页 + ?screen=control，│
│                平板可存书签；不单写一个页面）                       │
└───────────────┬──────────────────────────────┬─────────────────┘
                │ 心跳/领指令/回状态              │
        3× 电脑浏览器客户端                      2× 电视 APK
        （可控 + 可被控）                        （仅被控，新增 ControlChannel）
```

信息流只有三条，全部走既有 18000 端口：

1. 任一 Web 客户端的控制 screen 把指令写入服务端（**发完即走**，不依赖目标设备此刻在线）；
2. 所有设备每次心跳上报"我现在是什么状态"，顺带领取"服务端期望我变成什么"与"服务端认为我该是哪种模式"；
3. 控制 screen 轮询设备列表，把"模式 / 期望 / 实际 / 在线"并排展示。

## 五、设备身份与数据模型

### 5.1 设备身份（deviceId）与类型（kind）

- 客户端**首次运行时本地生成**：`dev-` + 8 位十六进制随机串（浏览器存 `localStorage['tvshow.deviceId']`；APK 存 SharedPreferences），此后终身不变。**身份与设备 IP 无关**（IP 变化的完整分析见第十三节）。
- 无需任何配对手册：任何设备第一次心跳即自动出现在设备列表，默认名"新设备-xxxx"，在控制 screen 里改名。
- 可选的预命名通道：沿用引导配置的既有做法，允许把 `{"deviceId":"dev-tv1","name":"一号电视"}` 放到设备本地覆盖路径（Android 为 `/sdcard/Android/data/com.digitalcenter.tvshow/files/device.json`），便于批量装机时预分配固定 ID。
- `kind` 由客户端自报：`tv`（APK）/ `pc`（桌面 UA）/ `tablet`（移动 UA + 触屏），仅用于设备列表图标与 bootRestore 默认值（5.3），**不构成任何权限差异**。

### 5.2 服务端存储 `server/data/devices.json`

```json
{
  "seq": 42,
  "devices": [
    {
      "id": "dev-a1b2c3d4",
      "name": "一号电视",
      "kind": "tv",
      "appVersion": "1.8",
      "registeredAt": "2026-10-24T09:00:00.000Z",
      "managed": false,
      "bootRestore": true,
      "desired": null,
      "ackedSeq": 38
    }
  ],
  "scenes": [
    {
      "id": "scene-morning",
      "name": "晨会",
      "createdAt": "2026-10-24T09:00:00.000Z",
      "steps": [
        { "deviceId": "dev-a1b2c3d4", "cmd": "show",   "args": { "entryId": "storage-monitor" } },
        { "deviceId": "dev-e5f6a7b8", "cmd": "rotate", "args": { "intervalSec": 15, "items": ["env-monitor", "security-cockpit"], "phaseSync": false } }
      ]
    }
  ]
}
```

| 字段 | 语义 |
| --- | --- |
| `seq` | 全局指令序号，每次 `POST /api/ctl/send` 自增；同时是"最后写入者胜"的仲裁依据 |
| `desired` | 该设备**当前期望的展示状态**（= 最后一条展示类指令），替换式更新，不排队；仅存展示类指令 |
| `managed` | **模式权威状态**：`true` 远程被控（跟随 desired、锁定展示操作）；`false` 本地控制（行为与现状一致）。随指令自动置 true；被「取消控制」或设备端开关交还时置 false（同时清空 desired）。注册时默认 `false`（本地控制） |
| `ackedSeq` | 设备最后一次确认已应用的指令序号；`desired.seq > ackedSeq` 表示"待送达/待应用" |
| `bootRestore` | 开机恢复开关（见 5.3） |
| `scenes` | 场景预设（见第九节） |
| `reported` / `lastSeenAt` | 设备上报的实际状态与最后心跳时间。**仅存内存**，不落盘 |

**持久化策略**：心跳每 3 秒一次，`reported`/`lastSeenAt` 若落盘会造成无意义的高频写盘——因此只在内存维护；服务端重启后丢失，但设备 3 秒内的心跳会把它填回来，无自愈问题。**只有身份信息（注册/改名/删除）、managed 翻转、desired 变化、场景增删改才写盘**，写盘沿用 `config.json` 的"临时文件 + rename"原子写与 `.bak` 备份惯例。

### 5.3 开机恢复（bootRestore）

设备侧 `ackedSeq` 只存内存（不持久化）：设备"开机"（APK 启动 / 浏览器打开页面）后第一次心跳带 `boot: true`，服务端若 **`bootRestore` 开且 `managed` 为远程被控**则无视 ackedSeq 重发 desired。效果：

> 把各设备调到某个状态后，任何一台断电重启（电视）或重新打开系统页面（电脑 kiosk 重开浏览器），都会自动回到设定好的画面——不需要有人到现场。

两条边界：

- **仅远程被控态生效**：本地控制的设备重启后走现状行为（本机设置里的"开机自动播放"等本地逻辑），不被服务端拉扯——"本地控制"必须是完整的自治；
- 默认值按 `kind` 区分：`tv`/`pc` **开**（挂墙展示设备刚需）；`tablet` **关**（平板是常用控制端，打开系统不应被自动拉回旧画面，要保持"拿来即用"）。默认值只在注册时落一次盘，之后可在设备卡片里逐台改。

## 六、指令集

每条指令的信封：`{ seq, cmd, args, issuedAt }`。v1 共 6 条，**对 Web 客户端与电视端同一套语义**。desired 只存展示类指令；"取消控制"不走指令，而是直接翻转 `managed` 标志（见 8.3，这样设备端开关与控制端按钮共用同一条最简路径）：

**展示类（应用后设备自动进入远程被控）**：

| cmd | args | 客户端行为 | 说明 |
| --- | --- | --- | --- |
| `show` | `entryId` | 进入单页展示（Android：`WebDisplayActivity`；camera 类型进 `CameraWallActivity`；Web 端：display/camera screen） | 对应"显示哪个页面" |
| `rotate` | `intervalSec`、`items[]`（入口 id 顺序即播放顺序）、`startedAt`、`phaseSync`（**默认 false**） | 把参数写入本机轮询设置，随后**立即进入轮询播放** | 对应"轮询" |
| `zone` | `slots: [entryId|null ×4]` | 写入本机分区设置并**立即进入 2×2 分屏** | 对应"分屏"；null = 该格不使用 |
| `home` | — | 回首页 | 远程被控停在首页（展示操作锁定）；"收工"建议用「取消控制」交还本地 |

**维护类（不改变模式，两种模式下都可用）**：

| cmd | args | 客户端行为 | 说明 |
| --- | --- | --- | --- |
| `refresh` | — | 刷新当前页 / 分屏时刷新全部四格 | 现场"画面卡了刷一下" |
| `sync` | — | 强制同步一次内容配置（`ConfigRepository.syncNow(force=true)`） | 排障用 |

**校验**（服务端 `POST /api/ctl/send` 时做，非法直接 400）：
- `cmd` 必须在白名单内；
- `intervalSec` 沿用本机现有取值范围 1–3600；`items`/`slots` 里的 `entryId` 必须存在于 `config.entries`；
- `zone.slots` 必须恰好 4 个元素。

**应用时二次校验**（客户端）：指令到达时页面可能已被删除（内容通道是全局的，随时可增删）。客户端按现有 `rotationEntries()` 的同款规则**跳过失效 id**；`show` 的目标不存在则回首页并在状态里上报 `lastError`。这是现有"服务端删页后轮询自动跳过"行为的自然延伸。

**轮询的"多屏同步切换"（`phaseSync`，默认关）**：
现有轮询计时公式 `index = floor((now - startedAt) / interval) mod n` 中 `startedAt` 是本机设置。下发轮询时若勾选"多屏同步切换"，则由**服务端生成同一个 `startedAt`**（当前时刻取整到间隔边界）发给所有目标设备——各设备时钟相同（内网 NTP）即**翻页时机完全一致**。不勾选（默认）时 `startedAt` 由各设备收到指令的时刻自定，各屏相位独立。

## 七、通信协议

### 7.1 `POST /api/ctl/beat` —— 心跳 + 领指令 + 回状态 + 同步模式（四合一）

设备侧唯一的上行接口。**3 秒一拍**（PC/平板的 Web 客户端与电视 APK 同一协议；七八台设备合计约 2.5 req/s，对服务端可忽略）。

```jsonc
// 请求（设备 → 服务端）
{
  "deviceId": "dev-a1b2c3d4",       // 客户端本地生成，首次心跳即注册
  "name": "",                        // 仅首次注册时可带自报名
  "kind": "tv",                      // tv | pc | tablet
  "appVersion": "1.8",
  "boot": true,                      // 本进程/本页面启动后的第一次心跳
  "ackedSeq": 38,
  "switchTo": "local",               // 可选，一次性模式开关意图：local | remote（见 8.3），送达前每拍重发
  "state": {                         // 上报实际状态；在首页时为 {"mode":"home"}
    "mode": "rotate",                // home | page | rotate | zone | camera | control
    "entryId": "env-monitor",
    "rotate": { "index": 1, "total": 3, "intervalSec": 15 }
  }
}

// 响应（服务端 → 设备）
{
  "ok": true,
  "name": "一号电视",
  "managed": true,                   // 模式权威状态；设备据此校正本地影子（开关位置）
  "serverTime": 1799990400123,
  "desired": { "seq": 41, "cmd": "rotate", "args": { /*…*/ } }   // 无待应用指令时为 null
}
```

**desired 下发规则**（服务端判定，客户端无脑执行）：

| 条件 | 响应中的 desired |
| --- | --- |
| `desired.seq > ackedSeq`（有待应用指令） | 下发 |
| `boot: true` 且该设备 `managed` 为远程被控且 `bootRestore` 开 | 无条件下发（开机恢复） |
| 其余 | `null`（这一拍就是纯心跳） |

客户端应用指令后，下一拍把 `ackedSeq` 更新为该指令的 `seq`，闭环完成。应用是**幂等**的：同一指令因网络重试被收到两次，第二次应用结果不变（写同样的本机设置、进入同样的模式）。

**`mode: control`**：Web 客户端打开设备控制 screen 时上报此模式——否则正在控别人的一台平板会在列表里显示"首页"，误导操作者。

**Web 端多标签页边界**：同一浏览器多标签共用 deviceId 与本机设置。kiosk 电脑与平板实际都是单标签使用；若真开了多标签，心跳以后上报者为准（状态可能互相覆盖）。v1 不做标签互斥（Web Locks 等），列为已知小边界。

### 7.2 其余接口（控制半边用，任何 Web 客户端可调）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/ctl/send` | `{ targets: ["dev-x","dev-y"], cmd, args }` → 对每台目标设备写 desired（`seq` 全局自增）并把 `managed` 置 true；`targets` 支持 `["*"]`。返回每台的受理结果 |
| POST | `/api/ctl/release` | `{ targets: [...] }` → 把目标设备 `managed` 置 false、desired 清空（**控制端「取消控制」**，与设备端开关共用同一条状态翻转路径） |
| GET | `/api/ctl/devices` | 设备列表（含内存中的 reported/lastSeen、managed、在线判定、待送达标记），控制 screen 3s 轮询它 |
| PUT | `/api/ctl/device/:id` | 改名、开关 `bootRestore` |
| POST | `/api/ctl/scenes` / `PUT|DELETE /api/ctl/scenes/:id` | 场景预设的保存 / 更新 / 删除（见第九节） |
| DELETE | `/api/ctl/device/:id` | 从档案移除（设备下次心跳会重新注册回来，配合改名实现"重置"） |

**在线判定**（服务端算好给控制 screen）：`lastSeenAt` 距今 <10s 在线；<60s "刚离线"；更久 "离线"。平板锁屏/关浏览器后自然变为离线，符合直觉。

### 7.3 传输选型对比（为什么 v1 用短轮询）

| 方案 | 指令延迟 | 实现代价 | 结论 |
| --- | --- | --- | --- |
| **短轮询 3s**（v1 采用） | 最坏 3s | 极低：一个普通 POST，复用现有 HTTP 栈与重试模式 | 对"替代走到设备前拿遥控器"的场景完全够用 |
| 长轮询（hold 20s） | 亚秒 | 中：服务端挂起连接 + 设备侧重试边界；`HttpURLConnection` 需调大读超时 | **升级路径**，接口形状不变（加 `?hold=1`），客户端可后切 |
| SSE | 亚秒 | 中：单向推送可行，但心跳/上报仍需第二条 POST 通道，且要处理断线重放 | 与长轮询收益相同，复杂度更高，不采用 |
| WebSocket | 亚秒 | 高：Node 零依赖下需手写帧协议，现有 `upgrade` 只为代理透传 | 不采用 |

## 八、模式开关：本地控制 ⇄ 远程被控（v4 核心）

### 8.1 两种模式

```
                任意展示类指令（show / rotate / zone / home）—— 自动、强制
   ┌──────────┐ ────────────────────────────────────────────▶ ┌──────────┐
   │ 本地控制  │                                               │ 远程被控  │
   │（现状行为）│ ◀──────────────────────────────────────────── │（驾驶权在 │
   └──────────┘   设备端开关 / 控制端「取消控制」—— 画面保持      │  控制端） │
                                  ▲                            └──────────┘
        （refresh / sync 维护类指令不改变模式）
```

**本地控制（`managed = false`，注册默认值，即"初次进入"的状态）**：行为与**现状完全一致**——遥控器/鼠标/键盘全部正常，轮询与分区按本机设置自主运行，"开机自动播放"等本地逻辑照旧。

**远程被控（`managed = true`）**：控制端下发任意展示类指令即进入（**自动、强制，本地无法拒绝**）：

- **画面强制切换**：无论设备当前在首页、展示页还是轮询设置/分区选页界面，指令到达即切换；
- **展示操作锁定**：首页宫格、展示页、轮询页、分区页、画面墙的本地内容操作不再生效——电视方向键/确定键透传被拦截、Web 端顶栏导航按钮与快捷键禁用、iframe `pointer-events: none`（与分区页现有做法一致）；
- **例外（关键）**：**模式开关永远可用**——Web 顶栏开关保持可点击；电视【菜单】键保持可开菜单（菜单里第一项即模式开关）。这是远程被控态下仅有的两个本地出口，取代 v3 的隐藏式逃生口手势；
- **受控标识**：屏幕角落显示半透明"远程被控"角标（被动指示，与开关状态一致，不遮挡大屏画面）；
- **离线保持**：远程被控态下网络中断，**画面继续显示**（本地设置已写入，轮询继续按本地时钟走），锁定与角标继续；服务端恢复后心跳自动续上；
- **重启恢复**：远程被控态 + `bootRestore` 开 → 重启后自动回到设定画面（5.3）；本地控制态重启走现状行为。

**交还本地（开关或「取消控制」）**：画面保持当前不变（只交还驾驶权，不改变像素——需要收场先发 `home` 再交还）；本地操作立即恢复；正在播放的轮询按已写入的本机设置继续，本地人员可随时按【返回】停止。

### 8.2 开关在两端的位置与形态

| 端 | 位置 | 形态 |
| --- | --- | --- |
| Web 客户端 | **顶栏**（所有 screen 常驻，含展示态） | 胶囊开关：「本地控制 ⬤ / 远程被控 ⬤」，当前态高亮；远程态用青色+角标呼应。切到"本地控制"时**先弹二次确认**（"退出远程被控，恢复本地操作？"）再生效；切到"远程被控"直接生效。切换后 Toast 提示 |
| 电视 APK | **【菜单】键控制菜单**（`TvDialogs`） | 菜单首项：「控制模式：本地控制 ▸ 远程被控」，按【确定】切换；**退出远程被控时弹确认对话框（默认焦点在「继续受控」，防误触）**，进入无需确认。本地态下菜单保持现有全部条目 + 该项；远程态下菜单**只显示**模式开关与关闭（其余条目属于"本地操作"，锁定） |

两端规则一致：**初次进入默认本地控制**；开关状态变化即时生效于本机（不等网络）；角标与开关、服务端档案三处显示同一状态。

### 8.3 开关的实现方式（比选与结论）

开关牵涉三个问题：状态记在哪、翻转如何同步、与控制端指令冲突听谁的。比选如下：

| 方案 | 做法 | 问题 | 结论 |
| --- | --- | --- | --- |
| A. 纯设备本地状态 | 模式只存设备端；设备在本地态忽略服务端指令 | **与"指令自动切回远程"直接矛盾**——本地态若忽略指令，控制端永远拿不回来；若不忽略，本地状态又会被指令覆盖，开关失去意义 | ❌ |
| B. 纯服务端状态，开关即远端调用 | 设备点开关 → 请求服务端改 `managed` → 等响应后再解锁 | 服务端失联时现场**点开关没反应**（锁死在远程态）——恰在最需要时失灵；且每次切换多一次请求 | ❌ |
| **C. 服务端权威 + 设备即时影子 + 心跳捎带意图（采用）** | 见下 | 冲突窗口 ≤3s（见下） | ✅ |

**方案 C 的机制**：

1. **权威状态在服务端**：`managed`（`devices.json`）是唯一权威，驱动控制 screen 显示与 bootRestore 判定。所有控制端动作（下发指令置 true、取消控制置 false）只改它。
2. **设备端维护即时影子**：`localMode`（内存态），决定本机此刻的实际行为（锁定/角标/UI）。翻转**立即生效、不等网络**——现场点开关瞬时见效，服务端失联也照常工作（这是否决方案 B 的关键）。
3. **两条同步路径**：
   - **服务端 → 设备**：心跳响应携带权威 `managed`，设备据此校正影子（如控制端远程取消控制，设备 ≤3s 内解锁）。展示类指令的应用本身也会把影子置为远程。
   - **设备 → 服务端**：现场拨动开关时，把一次性意图 `switchTo: "local"|"remote"` 塞进**下一次心跳请求**（≤3s 捎带送达，不新增接口、不新增请求频率）；服务端处理后将 `managed` 置为目标值，响应回带，设备确认一致后清除意图；未确认前每拍重发（幂等）。**离线时意图暂存，恢复后自动送达**——与指令同一套存储转发哲学。
4. **冲突规则（最后写入者胜，按到达顺序）**：
   - 现场拨"本地"→ 服务端 `managed=false`、desired 清空 → 控制端看到该设备变"本地"；
   - 控制端此刻再下发指令 → `managed=true` + 新 desired → 设备**自动切回远程**（用户明确要求的行为，开关不构成否决权）；
   - 3 秒窗口内的竞态（现场刚拨本地、指令同时在途）：**设备先应用已送达的指令（进远程），再执行本地的交还意图**——最终状态与"人手更快"一致，且两端状态收敛一致。窗口极短（≤3s），接受。

**为什么不用更复杂的机制**：长连接推送（让开关秒级同步）与双向确认协议，对"模式翻转"这种低频、允许 3 秒收敛的操作是过度设计；心跳捎带复用现有通道，设备端与服务端各加约 30 行即可。

### 8.4 与「取消控制」的关系

设备端开关与控制端「取消控制」按钮是**同一状态翻转的两个入口**（都落到 `managed=false` + desired 清空），语义完全一致；控制端按钮的价值在于"人不在设备旁"时远程交还，开关的价值在于"人就在设备旁"时即时交还。控制 screen 的设备卡片如实显示当前模式，无论它由哪一方翻转。

**二次确认的适用范围**：所有"退出远程被控"入口——设备端开关、电视菜单项、控制端「取消控制」——一律二次确认；"进入远程被控"与"下发展示指令"不需要确认（指令本来就自动接管，不存在歧义）。

## 九、场景预设

### 9.1 模型

一个场景 = 一组**按设备**的恢复指令快照，存于 `devices.json` 的 `scenes`（5.2 已示结构）：

```jsonc
{ "id": "scene-morning", "name": "晨会", "createdAt": "...",
  "steps": [ { "deviceId": "dev-a1b2c3d4", "cmd": "show",   "args": { "entryId": "storage-monitor" } },
             { "deviceId": "dev-e5f6a7b8", "cmd": "rotate", "args": { /*…*/ } } ] }
```

场景引用 deviceId，与 IP、在线状态无关；应用时设备离线则走存储转发补投递；场景里引用的设备已被删除则跳过该步并在结果里提示。

### 9.2 保存与应用

- **保存当前现场**：控制 screen 一键「存为场景」→ 命名。每台设备生成一条恢复指令：远程被控设备取其 `desired`；本地控制设备把当前 `reported` 转为等价指令（`page+entryId` → `show`；`rotate` → 带本机间隔与序列的 `rotate`；分屏 → `zone`；首页/画面墙 → 对应指令）；全部离线设备跳过并提示。
- **应用场景**：点场景按钮 → 服务端逐台下发 steps（等同批量 `send`，seq 逐台自增）→ 未被控的设备随之自动切入远程被控；应用完成后逐台回报状态，控制 screen 显示"已应用 x/y"。
- **管理**：重命名 / 删除；场景按钮常驻控制 screen 顶部，一键可达。

典型用途："晨会 / 来访 / 值守"三套现场，一键切换全馆 5 台设备的画面组合。注意：场景应用的是**指令快照**，之后各设备的内容变化（如页面改名）不影响场景里的 entryId 引用；被删页面的 step 应用时按第六节规则跳过。

### 10.2 电视端 APK（需出 1.8 包，只实现受控半边）

新增两个类，不改动现有同步/缓存逻辑：

**`net/ControlChannel.kt`** —— 心跳循环与传输
- 单例；`ExecutorService` 后台线程 3s 一拍（失败指数退避，最长 30s；恢复后自动回 3s），主线程回调；
- `current` 状态槽：各 Activity 在 `onResume` 时写入当前模式，心跳线程每拍读取；
- 收到 desired → 交 `CommandApplier` 在主线程应用 → 应用结果写回状态槽，下一拍 ack；`managed` 权威值与 `localMode` 影子随指令/开关维护；
- `switchTo` 意图入队/重发/确认清除；`deviceId` 生成与持久化、`boot` 标志管理。

**`config/CommandApplier.kt`** —— 指令 → 界面映射（核心表）

| 指令 | Android 行为 |
| --- | --- |
| `show` | `entry.type == camera` → `CameraWallActivity`；否则 `WebDisplayActivity`（`EXTRA_ENTRY_ID`） |
| `rotate` | `LocalSettings.saveRotation(...)`（含服务端 `startedAt`，不重置时钟）→ `WebDisplayActivity`（`EXTRA_ROTATION=true`） |
| `zone` | `LocalSettings.saveZones(...)` → `ZoneDisplayActivity` |
| `home` | 结束栈顶展示 Activity 回 `MainActivity`（不弹退出确认） |
| `refresh` | 栈顶 Activity 暴露的 `reloadCurrent()` |
| `sync` | `ConfigRepository.syncNow(force = true)` |

到达时机与切换方式：任意界面下指令即生效——`finish()` 当前展示 Activity 后 `startActivity` 目标（启动标志 `CLEAR_TOP`，保持单栈顶），**包括正在轮询设置/分区选页界面时**。指令应用失败（目标页面已删等）不阻塞后续指令，仅上报 `lastError`。

**模式开关（电视端）**：`TvDialogs` 控制菜单首项新增「控制模式：本地控制 ▸ 远程被控」；【菜单】键在远程被控态下**仍打开菜单**（`dispatchKeyEvent` 对 MENU 键豁免锁定），远程态菜单仅含模式开关与关闭项。

**展示操作锁定**：各展示 Activity 的 `dispatchKeyEvent` 在远程被控态下拦截方向/确定/返回键（仅 Toast 提示"远程被控中，可按【菜单】切换"）。

**状态上报点**（每处一两行）：`MainActivity` 报 `home`；`WebDisplayActivity` 按 `EXTRA_ROTATION` 报 `page`/`rotate`（轮询中带 `index/total/intervalSec`）；`ZoneDisplayActivity` 报 `zone`（带 4 格内容摘要）；`CameraWallActivity` 报 `camera`。

**与本机设置的关系**：指令的实现方式是"**把服务端期望值写进本机设置，再进入对应模式**"。远程被控期间本机设置即指令值；交还本地后，这些值就是本机设置，本地人员可随意改——两套机制无缝衔接，无指令时行为与现在完全一致。

- **分屏弹层**：2×2 可视化网格，每格下拉选页面/不使用；
- **取消控制**：对勾选设备交还本地（与设备端开关同一状态翻转，8.4），**执行前二次确认**；
- 3s 自动刷新设备列表；每次操作后立即手动刷一次，反馈更快；
- `/console` 直达时跳过首页直接进入本 screen（平板书签场景）。

## 十二、关键场景时序

1. **正常下发（含自动接管）**（平板上点"3 号电脑 → 显示存储集群"）：
   控制 screen `POST /api/ctl/send`（seq=43）→ 服务端写 desired、`managed=true` → 该设备下一拍（≤3s）领到指令 → 自动切为远程被控并强制切到存储集群页、锁定展示操作 → 下一拍上报 `page/storage-monitor` + ackedSeq=43 → 平板上的卡片变绿。
2. **现场人员用开关交还**：电脑3 前的操作员点击顶栏开关，**二次确认后**本机立即解锁、画面保持，角标消失（电视侧为【菜单】→ 控制模式 → 确认）→ 下一次心跳捎带 `switchTo:"local"` → 服务端 `managed=false`、desired 清空 → 平板上该卡片 ≤3s 内变为"本地控制"。若此后控制端再次下发指令，设备自动切回远程被控（开关不构成否决权）。
3. **控制端远程交还**：控制 screen 勾选设备 →「取消控制」→ 服务端 `managed=false`、desired 清空 → 设备下一拍看到 `managed=false` 解锁——与场景 2 是同一状态翻转的两个入口。
4. **逐台各显不同画面**（电视1显示画面1、电视2显示画面2、电脑3显示画面3）：
   **最基本的能力**——每台设备有自己独立的 `desired`，互不相干。只勾"一号电视"→ 选画面1 → 下发；再只勾"二号电视"→ 选画面2；再只勾"电脑3"→ 选画面3。多选/全选只是"同一指令发给一个勾选集"的便捷方式。
5. **场景一键切换**：点「▶晨会」→ 服务端按 steps 逐台下发 → 5 台设备各自切换并自动进入远程被控 → 控制 screen 显示"已应用 5/5"；某台离线则补投递，显示"已应用 4/5（1 台待送达）"。
6. **设备离线时下发**：desired 已落盘，卡片持续显示"待送达"；设备恢复后第一拍即领取应用。**控制端与被控端不需要同时在线。**
7. **设备断电/页面重开**：电视断电重启，或 kiosk 电脑浏览器重开页面 → 第一次心跳带 `boot:true` → 远程被控且 `bootRestore` 开 → 重发 desired → 自动回到设定画面。本地控制的设备重启走现状行为；平板默认关（见 5.3）。
8. **被控电脑 IP 变化**：DHCP 给电脑换了 IP → 设备身份不变（deviceId 与 IP 无关）→ 心跳照常、指令照常、名字与状态全保留，**无任何感知**。唯一注意点是浏览器访问地址变化会改变 origin（见第十三节）。
9. **服务端重启**：内存中的 reported/lastSeen 丢失 → 列表短暂显示"离线"→ 各设备 ≤3s 心跳填回；desired/managed/场景在磁盘上，不受影响。设备端 `localMode` 影子不落盘：重启后由第一次心跳的权威 `managed` 校正（偏差窗口 ≤3s，可接受）。

## 十三、边界、取舍与安全

### 13.1 电脑 IP 变化的影响分析

| 变化 | 影响 | 对策 |
| --- | --- | --- |
| **被控电脑自己的 IP 变了**（DHCP 续租换地址等） | **无影响**。设备身份是浏览器里随机生成并持久保存的 deviceId，服务端按 deviceId 匹配，从不按 IP；心跳/指令/档案/场景全部与 IP 解耦 | 无需任何操作。可选：给展示电脑做 DHCP 静态绑定，纯属整洁而非必需 |
| **同一台电脑换了访问地址**（如先用 `http://10.8.11.4:18000` 后改用 `http://server.local:18000`） | 浏览器 `localStorage` 按 **origin（协议+主机+端口）** 隔离——换地址即换 deviceId，同一台电脑会被识别为**两台设备**，旧条目离线残留 | **约定每台电脑固定用一个地址访问并锁定书签/主页**。旧条目在控制 screen 里删除即可（设备删除后下次心跳重新注册，配合改名实现重置） |
| **服务端 IP 变了**（影响最大，但与互控无关，是部署问题） | 所有客户端的访问地址与 APK 内置 `serverBaseUrl` 失效；控制通道与内容通道同源，一起受影响 | ① 服务器用**固定 IP / DHCP 保留 / 内网 DNS 名**（推荐 DNS 名，一劳永逸）；② 电视端用既有外部引导覆盖机制：把改了 `serverBaseUrl` 的 `config.json` push 到 `/sdcard/Android/data/com.digitalcenter.tvshow/files/`，免重装；③ 电脑/平板更新书签即可 |

结论：**设备身份设计已天然免疫"被控端 IP 变化"**；真正要管住的是两件事——每台电脑固定访问地址（origin 稳定），服务端地址固定或用域名。

### 13.2 其余边界与取舍

| 项 | 处理 |
| --- | --- |
| 时钟依赖 | 仅 `phaseSync`（默认关）依赖各设备时钟一致（内网 NTP 前提）；指令送达与 ack 全部基于 `seq`，与时钟无关 |
| 多个控制端同时操作 | 最后写入者胜（`seq` 全局递增），不做锁；两块平板、或平板+电脑同时控制也自然收敛 |
| 开关与指令的竞态 | ≤3s 窗口内"现场拨开关"与"指令在途"并存时，按到达顺序收敛：设备先应用指令、再执行交还意图；两端状态最终一致（8.3） |
| Web 端多标签页 | 同一浏览器共用 deviceId，状态以后上报者为准；kiosk/平板实际单标签，v1 不做标签互斥 |
| 指令引用的页面被删 | 下发时校验 400；应用时跳过/回首页并上报 `lastError`（见第六节）；场景 step 同规则跳过并提示 |
| 开关的边界 | 开关在设备本地生效、不受服务端控制——**现场任何人都能交还本地**，这是有意设计（驾驶权可争，注册权不可争：设备无法拒绝指令，也永远留在体系内）。锁定不是安全边界 |
| 写盘频率 | 心跳态仅内存；仅注册/改名/managed 翻转/desired 变化/场景增删改落盘 |
| 服务端负载 | 7 台 × 3s ≈ 2.5 req/s，可忽略；设备规模到几十台仍无压力 |
| **安全（互控的代价）** | 控制权 = 能打开 18000 的人，与既有管理后台"内网免鉴权"同一信任模型；**防火墙限源成为必须**。可选收紧手段（v1 不做，预留）：部署级共享令牌随引导配置下发、`--host` 限监听 |
| 明确不做 | 远程桌面/画面回传（重型页面的"看一眼"需求已由极速模式 `/shot` 覆盖）；2×2 以外的分屏布局；指令队列（只保留最后 desired）；公网访问与账号体系；设备退网/拒绝指令机制（指令永远自动接管） |
